VMware 虚拟机自编译 MT7921U 无线网卡驱动全记录

前言

在 VMware 虚拟机上使用外置的 MT7921U USB 无线网卡(MediaTek,VID:PID 0e8d:7961),想从源码自己编译驱动并手动加载,而不是依赖发行版自带的驱动。整个过程踩了不少坑:老源码与内核 API 不兼容、Ubuntu 头文件包含关系变化、模块签名校验、同名模块共存问题等等。

这篇文章完整记录整个流程、工具链、命令、遇到的问题和解决方法,最后附上持久化安装的方案(仅供记录,本文写作时未执行)。

一、环境与背景

1. 运行环境

项目 值
虚拟机 VMware (VMware 虚拟 USB 控制器)
操作系统 Ubuntu,内核 7.0.0-28-generic
无线网卡 MediaTek MT7921U,USB 接口,0e8d:7961
网络 有线 ens33(VMware 虚拟网卡,保证远程连接不掉线)

2. 为什么要自己编译

系统其实自带了能用的 mt7921u 驱动(接口 wlx… 都能识别出来)。自己编译的意义在于:

  • 使用最新上游源码,可能修复自带版本的问题、获得新特性;
  • 理解内核模块从编译到加载的完整链路;
  • 后续可以随意修改驱动代码按需定制。

3. 可行性评估(开始前必做)

开始之前先确认了这些前提是否满足:

检查项 检查命令 结果
硬件识别 lsusb ✅ 0e8d:7961 MediaTek Wireless_Device
内核头文件 ls /lib/modules/$(uname -r)/build ✅ 存在,指向 linux-headers-7.0.0-28-generic
编译工具链 gcc --version / make --version ✅ gcc 13.3.0 / GNU Make 4.3
驱动源码 ls mt7921/usb.c ✅ ~/code/mt76 含 mt7921u 驱动
固件 ls /lib/firmware/mediatek/ ✅ MT7922 系列固件(与 7921 共用)

结论:条件齐全,可行。

2. 踩坑 1:老驱动被一起编译,API 不兼容

现象:编译一开始就报 mt76x0/usb.c 大量错误,如 .stop / .config / .get_antenna 函数签名不匹配。

原因:kbuild 外编时,没有显式指定的 CONFIG_* 符号会沿用内核 .config 里的值。Ubuntu 内核把所有 mt76 子驱动都编成了模块,于是 MT76x0_COMMON 等老驱动也被拖进编译,而 mt76x0 太老,和内核 7.0 的新 cfg80211/mac80211 API 不兼容。

解决:只需要 USB 驱动链,把所有不需要的子驱动显式 =n(就是上面命令里那一长串 =n)。

现象:mt7921/main.c 里 .stop、.config、.set_rts_threshold、.get_txpower、.get_antenna、.set_antenna、.set_coverage_class 全部报”incompatible pointer type”。

五、手动加载驱动(换驱动)

1. 关键前提:模块签名

Ubuntu 内核开启 CONFIG_MODULE_SIG=y 但没有 CONFIG_MODULE_SIG_FORCE。含义:

  • 未签名的自编译模块可以加载,但会被内核打上 taint 标记;
  • 只有签名强制校验才会拒绝未签名模块。

所以自编译驱动能直接 insmod,代价是内核 taint。

七、持久化安装方法(本文只记录,未执行)

手动 insmod 只在本次开机有效:重启后 udev 会从 /lib/modules 重新加载系统自带的签名驱动,一切回到默认。

如果想让自编译驱动开机自动生效,下面两种方案(二选一)。

方法 A:复制到 updates 目录 + depmod(简单直接)

内核模块搜索路径中,/lib/modules/$(uname -r)/updates/ 优先级高于 kernel/。把编译产物放进去,modprobe 就会优先加载我们的版本:

之后重启,udev 识别到网卡时会 modprobe mt7921u,命中 updates 里的自编译版本。无线 USB 驱动在用户态由 udev 加载,不需要改 initramfs。

回滚:删掉 updates 里拷贝的文件再 sudo depmod -a,即恢复系统自带驱动。

缺点:内核一旦升级(换 $(uname -r)),updates 目录跟着变,需要重新编译重装;无免密 sudo 时每次都要输密码。

方法 B:DKMS(内核升级自动重编译,推荐但配置略繁琐)

DKMS 能在每次内核升级后自动重新编译模块,免去手工维护。mt76 是”一树多模块 + 子目录”结构(mt7921/ 里有 mt7921-common.ko / mt7921u.ko),需要专门写一份 dkms.conf:

持久化的其他注意点

  • 模块签名/taint:自编译未签名模块即使持久化,每次加载仍会打 OE taint。若在意,可自建密钥给模块签名并 MOK 入内核信任链(在 VMware 且未开 Secure Boot 的环境通常没必要)。
  • 源码补丁保留:持久化依赖 ~/code/mt76 里的两个补丁(mt76.h 加 version.h、tx.c 换 airtime_check),升级源码时记得重新评估。
  • 与系统自带驱动互斥:只要 updates/ 或 DKMS 生效,系统自带的同名模块就不会被加载,无需 blacklist。

总结

把整个流程浓缩成一句话:工具链匹配 + 源码版本匹配 + API 适配 + 正确处理同名模块与签名,内核模块自编译就能顺利跑起来。

值得记住的点:

  • ✅ 内核驱动外编:头文件版本 = 运行内核版本,先 lsmod 看依赖链,再动手;
  • ✅ 源码尽量切最新分支,别在旧分支上手工适配几十个 API;
  • ✅ kbuild 外编要显式 =n 关掉不需要的驱动,否则内核 .config 会把它们一起拖进来;
  • ✅ Ubuntu 未开 MODULE_SIG_FORCE,自编译未签名模块能加载,代价只是 taint;
  • ✅ 同名模块互斥,换驱动 = 逆序 rmmod + 顺序 insmod;
  • ✅ 手动加载是一次性的,持久化用 updates/ + depmod 或 DKMS。

以后内核升级了,记得重新走一遍”编译 → 验证”流程。
