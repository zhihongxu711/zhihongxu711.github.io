GitHub 私有仓库 + Actions 自动部署 Hexo 博客

前言

搭建 Hexo 博客后，一直用 hexo deploy 手动部署：本地写完文章 → hexo generate → 推送 gh-pages 分支。

这套流程有两个痛点：

  1. 源项目没有备份。hexo deploy 推上去的只是 public/ 目录的构建产物，即一堆静态 HTML。一旦本地项目丢失，文章源文件和配置就全没了。
  2. 每次部署都要手动跑命令，还容易漏步骤。

于是我把流程升级为：私有仓库保存源码 + GitHub Actions 自动构建部署。写完文章，git push 一下就自动上线。

为什么这样设计

Hexo 博客其实有两部分：

  • 源项目：Markdown 文章、_config.yml 配置、主题 —— 需要版本管理和备份；
  • 构建产物：hexo generate 生成的静态 HTML —— 就是当前线上页面。

如果把源码直接放进公开的 username.github.io 仓库，源码就公开了。更合理的做法是：

  • 源码放私有仓库（hexo-blog）；
  • 构建产物推送到公开的 username.github.io 仓库；
  • 中间用 GitHub Actions 自动化。

踩坑记录

坑 1：OAuth Token 不能推送 workflow 文件

一开始用 gh 登录的 OAuth Token 通过 HTTPS 推送，被拒绝了：

GitHub 出于安全考虑，创建或更新 workflow 文件要求 Token 带有 workflow scope。解决办法二选一：

  • 给现有 Token 加 scope：gh auth refresh -s workflow；
  • 或者改用 SSH 推送（SSH 密钥没有这个限制）。

坑 2：Fine-grained Token 权限不足，403

第一次部署失败：

这说明 Token 认证成功了，但没有目标仓库的写权限。原因是 Fine-grained Token 里：

  • 要么 Repository access 没选中目标仓库；
  • 要么 Contents 权限没改成 Read and write（默认是 No access）。

改好权限即可。注意：只改权限、Token 字符串不变的话，Secret 无需更新。

坑 3：SSH 22 端口被网络代理拦截

总结

用 私有仓库 + Actions 自动部署 Hexo 博客的好处：

  • ✅ 源码有云端备份，本地丢失也能完整恢复（文章、配置、主题都在）；
  • ✅ 源码不公开，私有仓库保护文章草稿和配置；
  • ✅ 一键发布，写完 git push 自动构建上线；
  • ✅ 构建过程透明，Actions 日志可随时排查问题。

现在写博客的流程简化为：写文章 → git push → 自动上线。
